## 4. Hypothesis (written BEFORE running the test)

**This hypothesis was NOT written before the test.** It was written after the first runs, while hunting, and it is recorded here unchanged.

Original hypothesis, as stated: *T1059.003 is a true remote file execution using PowerShell.*

Original query:

```
FROM logs-windows.powershell_operational-default
| WHERE host.name == "win11-victim"
    AND event.action == "Execute a Remote Command"
    AND file.extension == "psm1"
```

The preview returned a good amount of events, which I took as confirmation.

**Why it was wrong:**

1. **Wrong technique and data source.** T1059.003 is Windows Command Shell (`cmd.exe`), detected in Sysmon event 1. PowerShell is T1059.001, already covered in Lab 02.
2. **The `event.action` filter doesn't isolate remoting.** `Execute a Remote Command` is the task label PowerShell script block logging events carry, and it applies to local script blocks too. This explanation is from knowledge of the logging; I did not inspect the raw events from that preview.
3. **`.psm1` files are PowerShell modules.** Hits are most likely PowerShell loading its own modules, which happens on any PowerShell start and is unrelated to the Atomic.
4. **A busy preview is not evidence.** The query was fitted to whatever data came back instead of predicted from the Atomic.

**Corrected expectation (written after the fact, not a prediction):**

- Expected telemetry: Sysmon event 1 (`event.code` 1), `process.name` `cmd.exe`.
- Expected process chain: `powershell.exe` → `cmd.exe /c <path to .bat>`.
- What would prove this wrong: no `cmd.exe` child of PowerShell around the run time, or no batch path in `process.command_line`.

## 6. Evidence

1. **Execution confirmed on victim:** Sysmon event 1 (channel `Microsoft-Windows-Sysmon/Operational`) records `cmd.exe` created with the batch path in its command line. Sysmon's own `RuleName` tag on these events reads `technique_id=T1059.003`, but that tags every `cmd.exe` and is not a detection. The output of the batch's `dir` command was not captured, so execution is shown by the process creation.
2. **Process chain (case 1):**

| Time (UTC) | process.name | process.entity_id | process.parent.name | process.parent.entity_id | process.command_line |
| --- | --- | --- | --- | --- | --- |
| before child (not captured) | powershell.exe | {3DB7E871-B95E-6AC1-7F02-000000000D00} | n/a | n/a | `"powershell.exe" & {Start-Process \""C:\Users\Alter\AppData\Local\Temp\AtomicRedTeam\..\ExternalPayloads\T1059.003_script.bat\""}` |
| 2026-10-04 02:26:39.692 | cmd.exe | {3DB7E871-B95F-6AC1-8302-000000000D00} | powershell.exe | {3DB7E871-B95E-6AC1-7F02-000000000D00} | `C:\WINDOWS\system32\cmd.exe /c ""C:\Users\Alter\AppData\Local\Temp\ExternalPayloads\T1059.003_script.bat" "` |

   Notes: Windows adds the `/c` itself when `Start-Process` opens a `.bat`, which is why the Atomic never mentions `cmd`. The parent path (`Temp\AtomicRedTeam\..\ExternalPayloads\`) and the child path (`Temp\ExternalPayloads\`) resolve to the same file.

3. **Query that returns it** (index pattern `logs-windows.sysmon_operational-default`):

```
FROM logs-windows.sysmon_operational-default
| WHERE host.name == "win11-victim"
    AND event.code == "1"
    AND process.name == "cmd.exe"
| KEEP @timestamp, process.name, process.entity_id, process.parent.name,
       process.parent.entity_id, process.command_line, process.parent.command_line
| SORT @timestamp DESC
```

4. **Hypothesis check:** The original PowerShell-log hypothesis did not match (section 4). The corrected expectation matched: Sysmon event 1 showed `powershell.exe` → `cmd.exe /c` with the batch path on every run.

## 7. Detection rule

- **Name:** `CSN - cmd execution` · **Type:** ES|QL · **Index:** `logs-windows.sysmon_operational-default` · **Severity:** low (risk 21)
- **ATT&CK on the rule:** Execution (TA0002) → T1059 → T1059.003
- **Schedule:** every 5 minutes, lookback `now-6m`
- **History:** revision 0 created 2026-10-03 19:56:35 local; it was the hunting query saved as a rule, so it alerted on every `cmd.exe` on the host. Revision 1 saved 20:18:33 local, before the first event used for testing.
- **False-positive note on the rule:** "Admin scripts run from PowerShell are false positives"

```
FROM logs-windows.sysmon_operational-default METADATA _id, _version, _index
| WHERE event.code == "1"
    AND process.name == "cmd.exe"
    AND process.parent.name == "powershell.exe"
    AND (TO_LOWER(process.command_line) LIKE "*.bat*"
         OR TO_LOWER(process.command_line) LIKE "*.cmd*")
| KEEP @timestamp, host.name, user.name, process.entity_id, process.command_line,
       process.parent.entity_id, process.parent.command_line, _id, _version, _index
```

- `event.code == "1"`: Sysmon process creation.
- `process.name == "cmd.exe"`: the child hop.
- `process.parent.name == "powershell.exe"`: the parent hop.
- `.bat` / `.cmd` clause: the batch file path in the child's command line (`...T1059.003_script.bat`). `TO_LOWER` is used because ES|QL `LIKE` is case-sensitive.
- `METADATA _id, _version, _index`: required on non-aggregating ES|QL rules so alerts link to and dedupe on the source event.
- **Source:** written from scratch, drafted with assistance from Claude and tested by the analyst.

## 9. False positives and gaps

- **False positives:** any admin or maintenance `.bat` or `.cmd` launched from PowerShell (case 2). Exclude by known script path or user once the baseline is understood.
- **Misses:**
  - PowerShell launching `cmd /c <inline command>` with no batch file (case 4 shows this directly). It is still T1059.003.
  - `cmd.exe` launched by any parent other than `powershell.exe` (Explorer, other `cmd.exe`, WMI, services), as in case 3 and the 20:23 events.
- **Untested:** the `.cmd` branch of the clause has never fired. The only `.cmd` event had an Explorer parent and was excluded first.
- **Rule scope:** the rule is not pinned to one host, so it covers any host sending to that index.
