## 1. Result

Atomic Test 13 was run from the Kali attacker over an SSH PowerShell session. The custom rule fired on the re-run, about 4 minutes after the event. The rule is broad: it alerts on every PowerShell process started inside the session, including prep and cleanup commands, and it is blind to the same technique run through other processes.

- **Technique executed on victim:** Yes (Evidence 1)
- **Detected on first run:** No. No rule existed yet (rule created 13:51, first run 11:20). The activity was located in Sysmon telemetry using known timestamps from command history, which is a lookup, not a detection.
- **Detection rule written:** Yes. CSN - Powershell remote execution (SSH/WinRM)
- **Fired on re-run:** Yes. Alert at 20:42:09 local for the event at 20:38:09
- **Verdict:** Needs tuning. Detection works for this test, with the gaps listed in section 9.

## 7. Detection rule

- **Name:** CSN - Powershell remote execution (SSH/WinRM)
- **Type:** EQL (Event Correlation in the Kibana UI). It matches single process-start events, not sequences.
- **Settings:** severity Medium, risk score 47, runs every 5 min, look-back 1 min, max 100 alerts per run
- **Index patterns:** Elastic default set plus `logs-windows.sysmon_operational-*`. The matched events came from the Sysmon index.
- **Tested against:** revision 3

```
process where host.os.type == "windows" and event.type == "start" and
  process.name : ("powershell.exe", "pwsh.exe") and
  (
    process.parent.name : "wsmprovhost.exe" or
    (process.parent.name : "pwsh.exe" and process.parent.args : "-sshs")
  )
```

**Which clause matched:** the final hop only (powershell.exe with parent pwsh.exe -sshs), through the second branch. The rule does not see the earlier hops (cmd.exe, sshd.exe); they are context from the evidence table. The `wsmprovhost.exe` branch was never exercised.

R3 added a process.name filter limiting matches to powershell.exe and pwsh.exe. The reason for the change was not recorded. Before R3, the rule alerted on whoami.exe (13:51:58). After R3, the query should no longer match a process with that name (untested).

## 9. False positives and gaps

**False positives**
- The rule alerts on any PowerShell process run through an SSH or WinRM session, including the atomic's prep and cleanup steps. Legitimate admin use of PowerShell remoting will match.
- Under R0, `whoami.exe` in the session alerted. R3 removed that match.

**Gaps**
- **PowerShell logging:** no 4103/4104 events were observed for this test. Cause unknown. Possible causes: script block logging not enabled, the PowerShell 7 log channel not collected, or events not reaching Elastic.
- **WinRM branch** untested.
- **Other processes:** a command run through SSH with cmd.exe or another non-PowerShell process would not match this rule.
- **Latency:** scheduled rule, so alerts arrive up to about 5 minutes after the event.
